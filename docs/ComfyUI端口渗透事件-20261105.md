# ComfyUI 8000 端口渗透事件与处置（2026-11-05）

> 起因：用户反馈「明明第一条成功了，后面两条全失败」。
> 排查结论：**不是模型/参数问题，是 ComfyUI 被公网暴露后遭持续渗透，
> 攻击者的操作把正在跑的采样 `Global interrupt` 掉了。**

---

## 一、现象

用户连续提交 3 条 AI 工作室视频：

| 任务 | 提交 | 完成/失败 | 结果 |
|---|---|---|---|
| 225 | 08:13 | 08:25 | ✅ 成功（11 分钟，未被打断）|
| 461 | 08:38 | 08:39:51 | ❌ ComfyUI 未返回产物（outputs=['205']）|
| 574 | 08:43 | 08:47:57 | ❌ 同上 |

两条失败都退了 50 币（钱包流水 ledger #641 / #645 可查）。

## 二、根因

### 1. ComfyUI 裸奔公网

```
ExecStart=/opt/comfyui/venv/bin/python main.py --listen 0.0.0.0 --port 8000
iptables -L INPUT  →  空（无任何规则）
ufw status         →  inactive
```

8000 端口对全网开放。所有 worker（sugus / heygirl 的 short worker + 四个
custom-video worker）**都走 `127.0.0.1:8000`**，从来没有外网访问需求。

### 2. 有人在持续渗透

日志里的攻击尝试（按时间）：

| 时间 | 手法 | 结果 |
|---|---|---|
| 11-03 19:42 | 上传探测图 `i3023_up.png` | 写入成功 |
| 11-05 06:21 | Pickle RCE：`i34297.pt` 内嵌 `system('id > ...; hostname; cat /proc/1/cgroup; nvidia-smi -L; ls -l /dev/nvidia...')` | **未执行**（无回写文件）|
| 11-05 08:10 | 绝对路径写入 `i34574_abs.txt` = `ABS34574-WRITE` | 写入成功（证明可写 output 目录）|
| 11-05 08:21 | 表达式注入 `__import__('os').popen('id').read()` | 被 simpleeval 拦截 |
| 11-05 08:33 | Pickle RCE `i3464_rce.ckpt` | **未执行** |
| 11-05 08:39 | `Global interrupt (no prompt_id specified)` | **打断了任务 461** |
| 11-05 08:47 | `Global interrupt` | **打断了任务 574** |
| 11-05 08:50 | 路径穿越目录 `..%2F..%2Fuser%2Fdefault`、`i34650_trav.py` | 目录被创建 |
| 11-05 08:52 | `i34650_rel.txt` = `X-I34650`（相对路径写测试）| 写入成功 |

`Global interrupt` 全日志出现 **14 次**。ComfyUI history 里两条失败任务的
状态是 `execution_interrupted`（不是 `execution_error`），这是被外部中断的
明确证据——worker 侧只能看到「未返回产物」。

### 3. 攻击是否成功

**没有成功执行任意命令**：

- `i34297_pwn.txt`、`ckpt_rce_i3464.txt` 均不存在 → pickle payload 未执行
- 无异常挖矿进程（`ps aux --sort=-%cpu` 最高是 ComfyUI 自身）
- 无异常外连（除 ComfyUI 的 8000 连接外，只有 1.1.1.1 DNS 和既有服务）

但攻击者**已经证明**可以：
- 往 `ComfyUI/output/` 任意写文件
- 制造路径穿越目录
- 打断任何正在进行的生成任务

## 三、处置

### 已做（2026-11-05）

1. **封锁两个攻击 IP**（iptables DROP）
   ```
   155.69.183.11
   171.83.49.40
   ```
2. **强制断开它们的既有 TCP 会话**（`ss -K`），之后 8000 上无任何外部连接
3. 确认攻击未成功（无回写文件、无异常进程/外连）
4. 新增 `.zcode/gpumig/restrict_comfyui.sh`：
   - 默认 DROP，白名单只有 `lo` / `127.0.0.1` / 本机公网 IP
   - 只对 8000 端口生效，不碰 22 / 9100 / 9835
   - 幂等、可 `--status` 查看、`--flush` 应急回滚
   - 自动持久化到 `netfilter-persistent`

### 用法

```bash
# 应用默认策略（仅本机可访问 8000）
bash restrict_comfyui.sh

# 额外放行指定 IP（例如运维机）
bash restrict_comfyui.sh 203.0.113.10

# 查看当前规则
bash restrict_comfyui.sh --status

# 应急回滚（恢复无限制）
bash restrict_comfyui.sh --flush
```

## 四、后续建议

1. **定期检查**：`bash restrict_comfyui.sh --status`，看有没有陌生 IP 被放行
2. **清理攻击残留**：`/opt/comfyui/ComfyUI/output/` 下的 `i34*` 探测文件、
   `..%2F..%2Fuser%2Fdefault` 路径穿越目录可以删掉
3. **考虑改绑 127.0.0.1**：所有 worker 都走本机，`--listen 127.0.0.1`
   比维护白名单更彻底。当前选择保留 0.0.0.0 + 白名单，如需切换：
   ```
   改 /etc/systemd/system/comfyui.service 的 --listen 0.0.0.0 → 127.0.0.1
   systemctl daemon-reload && systemctl restart comfyui
   ```
4. **API Key 加固**（长期）：ComfyUI 本身无鉴权，暴露即等于给出完整生成能力。
   若确需外部访问，应放在带鉴权的反代（nginx + Basic Auth / mTLS）后面。

## 五、教训

- 这台 GPU 机 2026-11 换机后重建，`--listen 0.0.0.0` 是部署脚本的默认值，
  当时没意识到 8000 会直接暴露到公网（旧机可能有上游防火墙挡着）。
- **换机/重建时必须检查监听地址**，尤其是 ComfyUI 这种无鉴权服务。
- 生成失败先查 ComfyUI history 的 `status.status_str`：
  - `execution_error` → 模型/参数/显存问题
  - `execution_interrupted` → 被外部打断，查 `Global interrupt`
