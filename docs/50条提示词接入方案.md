## 二、架构决策

### 决策 1：每条提示词 = 一条数据库记录（不是配置池）

```
lp_video_preset
  code = gs-01 .. gs-50     ← API 唯一寻址键
  prompt                    ← 该条专属提示词
  lora_chain (JSON)         ← 该条专属 LoRA 链
  duration_sec              ← 该条时长
  cover_url / preview_url   ← 复用 media/gs/ 已有素材
```

**为什么不塞进 `wf_prompts.json` 的池子**：池子是「A 风格随机挑一条」，你要的是「第 17 条就是第 17 条」。
API 必须能精确寻址单条，否则无法验收、无法调优、无法单独下架。

### 决策 2：复用一份工作流 JSON，LoRA 链运行时动态拼

反编译对比已证明：

```
fingering vs MysticXXX（去掉 901 节点和 prompt）→ IDENTICAL
fingering vs CumFacial（去掉 901 节点和 prompt）→ IDENTICAL
其余 26 个节点逐字段完全相同
```

所以**不新建工作流**。worker 拿到 `lora_chain` 后动态生成 `LoraLoaderModelOnly` 节点替换掉 `900/901`。
好处：加风格只改数据库，不碰四站文件；工作流里验证过的 INT8/注意力补丁参数不会丢。

### 决策 3：prompt 由后端下发，worker 不再随机覆盖

```
现在：后端存 prompt → worker pick_prompt(style) 随机覆盖 → 实际提示词与后端无关
改后：后端存 prompt → worker 用 task.prompt → pick_prompt 仅作兜底（老任务）
```

## 三、数据模型

```sql
CREATE TABLE IF NOT EXISTS `lp_video_preset` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `code`         VARCHAR(32)  NOT NULL DEFAULT '' COMMENT 'API 寻址键，如 gs-01',
  `title`        VARCHAR(120) NOT NULL DEFAULT '' COMMENT '卡片标题',
  `prompt`       TEXT         NOT NULL COMMENT '提示词（英文，<=1000 字符）',
  `category`     VARCHAR(32)  NOT NULL DEFAULT '' COMMENT '动作分类：blowjob/cowgirl/doggy/cumshot/solo/other',
  `lora_chain`   JSON         NULL COMMENT '[[文件名, 强度], ...]，空=仅 motion_enhancer',
  `duration_sec` TINYINT UNSIGNED NOT NULL DEFAULT 8 COMMENT '生成时长(秒)',
  `cover_url`    VARCHAR(500) NOT NULL DEFAULT '' COMMENT '封面（media/gs/xx.jpg）',
  `preview_url`  VARCHAR(500) NOT NULL DEFAULT '' COMMENT '参考视频（media/gs/xx.mp4）',
  `weigh`        INT NOT NULL DEFAULT 0,
  `status`       TINYINT NOT NULL DEFAULT 1 COMMENT '1启用 0下架',
  `created_at`   DATETIME DEFAULT NULL,
  `updated_at`   DATETIME DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_code` (`code`),
  KEY `idx_status_weigh` (`status`, `weigh`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='AI视频生成预设（每条=一套提示词+LoRA+时长）';
```

50 行种子数据由 `php/sql/upgrade_video_preset.sql` 导入。

## 四、API 契约

### 4.1 新增：预设列表

```
GET /api/customVideo/presets          （公开，无需登录）
→ { code:"00000", data:{ list:[
     { code:"gs-01", title:"Deepthroat (POV) - 8s", category:"blowjob",
       cover_url:"/ai/media/gs/01.jpg", preview_url:"/ai/media/gs/01.mp4",
       duration_sec:8 }
   , ... 50 条 ] } }
```

只返回展示字段，**不返回 prompt 和 lora_chain**（避免提示词被抓取）。

### 4.2 扩展：提交

```
POST /api/customVideo/submit          （需登录，multipart）
  image          必填  jpg/png/webp ≤10MB
  type           video
  preset_code    新增  如 gs-17，**优先于 style**
  style          兼容  旧的 fingering/mysticxxx/cumfacial 仍可用
  agreed_policy  1
  confirm_paid   可选
```

后端逻辑：

```
if preset_code:
    查 lp_video_preset where code=? and status=1
    未找到 → PARAM_ERROR "Preset not found"
    style    = code
    label    = title
    prompt   = prompt          ← 不再为空
    lora     = lora_chain
    duration = duration_sec
elif style:                    ← 旧路径，STYLES 常量兜底
    ...
```

落库 `lp_ai_task.content`：

```json
{ "style":"gs-17", "label":"Make sex video", "prompt":"...",
  "image_url":"...", "lora_chain":[[...]], "duration_sec":8,
  "paid_tokens":0, "retry":0 }
```

`/pending` 已经会返回 `prompt`，**只需补 `lora_chain` 和 `duration_sec` 两个字段**。

## 七、实测成本（本轮已在 GPU 上跑过）

| 配置 | 时长 | 耗时 |
|---|---|---|
| 2 层 LoRA（现状） | 3s | 90.6s |
| 4 层 LoRA（+slop_bounce +ass_jiggle） | 3s | 160.1s |
| 4 层 LoRA | 3s（重复跑，验缓存） | 140.6s ← 缓存只省 12% |
| **4 层 LoRA** | **7s（生产时长）** | **611.6s（10.2 分钟）** |
| 6 层 LoRA | 3s | 220.1s |

**结论**：
- LoRA 层数**没有硬上限**（6 层跑通、产物非黑），但耗时随层数线性上涨；
- 合并权重每轮都重付，**不存在「多挂几个不心疼」**；
- 8 秒片 + 2 层 LoRA 预估 **约 5–6 分钟/条**，四站共用一张卡串行。

⚠️ **这是本方案最大的现实约束**：50 条全量回归验证需 GPU 连续跑 **4–5 小时**，
且线上高峰期用户排队会明显变长。建议按第八节的灰度节奏推进。

## 八、实施顺序（分阶段，每阶段可回滚）

| 阶段 | 内容 | 验证 | 可回滚 |
|---|---|---|---|
| **P0** | worker 修 prompt 优先级（`task.prompt` 优先） | 提交带 prompt 的任务，worker 日志应打印该 prompt 而非随机池 | 改回 1 行 |
| **P1** | 建表 + 导入 50 条种子数据 | `SELECT COUNT(*)` = 50；`/presets` 返回 50 | `DROP TABLE` |
| **P2** | 后端 `presets()` + `submit()` 认 `preset_code` | 用 curl 提交 `gs-17`，DB `content` 里 prompt 正确 | 代码回滚 |
| **P3** | worker 动态 LoRA 链 + 时长 | sugus 单站手动跑 2 条不同 preset，确认 LoRA 与时长生效 | 恢复 tpl 备份 |
| **P4** | 前端接线（sugus→heygirl→kelymi/kiss） | 真实浏览器点卡片 → 生成 → 产物动作匹配标题 | 前端版本回滚 |
| **P5** | 逐条验收 50 条 | 每条出片、动作与标题相符、非黑 | — |

**建议先做 P0**：这是当前的一处实质 bug（后端传的 prompt 被静默覆盖），单独修就有价值，
且改动最小、风险最低，能立刻验证整条链路。

## 九、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| worker 改动影响四站 | `/opt/cv/tpl/worker_gpu.py` 四站共用，配错 = 所有视频生成失败 | 先在 `/opt/cv/sugus/` 灰度单站，成功再推 tpl |
